# Chapter 4
# Archive Query and Literature Ephemeris Retrieval

---

# 4.1 Overview

After resolving the target, the next stage of the pipeline attempts to determine whether the target already has one or more published planetary ephemerides.

Rather than immediately performing an expensive blind transit search, the pipeline first consults a **locally stored export of the NASA Exoplanet Archive TOI catalog**.

If one or more orbital periods are found, these literature values are later used to **guide and refine** the Transit Least Squares (TLS) search instead of searching the entire period space.

This significantly reduces computational cost while also reducing the probability of converging to an alias period.

---

# 4.2 Scientific Motivation

Searching an entire light curve for transits is computationally expensive.

For a period range of

```
0.5 day
↓

30 days
```

TLS must evaluate thousands of trial periods.

However, if the orbital period is already known from previous observations, the search can be restricted to a very narrow interval

```
Parchive ± ΔP
```

where

```
ΔP ≈ min(0.01 d, 0.002 P)
```

Consequently,

- runtime decreases,
- false positives decrease,
- ephemerides are refined using the current TESS observations.

# 4.4 Architecture

The archive subsystem consists of two layers.

```text
PeriodStage.lookup_archive()

        │

        ▼

catalogs/nasa_archive.py

        │

        ▼

Local NASA Archive CSV

        │

        ▼

Published Planet Information
```

The `PeriodStage` does **not** perform any archive parsing itself.

Instead, it delegates all catalog operations to

```python
query_archive_all()
```

maintaining a clear separation between

- scientific workflow

and

- catalog management.

# 4.5 Data Source

Unlike many pipelines that query the NASA Exoplanet Archive online for every target, the current implementation operates on a **local CSV export**.

The CSV is searched in two ways.

### Environment variable

```text
TESS_PIPELINE_ARCHIVE_CSV
```

takes highest priority.

---

### Automatic discovery

Otherwise,

the pipeline searches upward through the project tree

```
project/

    data/

        TOI_*.csv
```

choosing the newest matching export.

---

Advantages

- offline operation
- reproducibility
- zero network latency
- deterministic results

# 4.7 Loading the Archive

The archive is loaded only once.

```python
@lru_cache(maxsize=4)
```

is applied to

```python
_load_local_archive_rows()
```

Consequently,

```text
Disk

↓

Memory

↓

Cache

↓

Future Queries
```

Repeated searches for hundreds of targets therefore avoid repeated disk I/O.


```
tid

tic_id
```

Rows satisfying

```
row TIC == requested TIC
```

# 4.9 Record Ranking

Multiple rows often exist for one TIC.

For example,

```
TOI

CP

KP

PC

FP
```

may all appear.

The pipeline therefore ranks records before selecting them.

---

Ranking criterion

```python
_record_sort_key()
```

returns

```
(

Disposition Rank,

Planet Number,

TOI Number

)
```

where

Disposition Rank

| Disposition | Rank |
|--------------|------|
| CP | 0 |
| KP | 1 |
| PC | 2 |
| APC | 3 |
| FA | 4 |
| FP | 5 |
| Unknown | 99 |

Thus

```
Confirmed Planet

↓

Known Planet

↓

Planet Candidate

↓

False Positive
```

---

This ranking ensures that the most reliable literature solution is processed first.

# 4.10 Duplicate Removal

Multiple entries frequently correspond to the same TOI.

The pipeline therefore keeps only

```
First occurrence of each TOI
```

using

```python
seen_tois = set()
```

Consequently,

```
TOI-270

Variant A

Variant B

Variant C

↓

Keep Variant A
```

# 4.16 Computational Complexity

Assume

```

```

The operations are

| Operation | Complexity |
|------------|------------|
| Load CSV | O(N) |

```

```

# 4.18 Current Limitations

Although robust, several limitations remain.

---

## Entire CSV is Loaded

Each query scans the full archive.

For a TOI catalog containing

```
100,000+

rows
```

this becomes inefficient.

A dictionary

```
TIC

↓

Rows
```

constructed once at startup would reduce lookup complexity from

```
O(N)

↓

O(1)
```

---

## Only Local Archive

The current implementation never queries

- NASA TAP
- Exoplanet Archive API
- MAST API

Consequently,

recently confirmed planets are unavailable until a new CSV is downloaded.

---

## No Version Tracking

The returned metadata contains only

```
Local NASA Archive TOI export
```

It does not record

- archive release date,
- download timestamp,
- DOI,
- archive version.

This reduces long-term reproducibility.

---

## Limited Planet Metadata

Only a few parameters are extracted.

Potentially useful quantities include

- eccentricity,
- inclination,
- stellar radius,
- stellar mass,
- transit duration,
- impact parameter,
- discovery method,
- disposition score.

These could strengthen downstream priors.

---

## CSV Parsing

The implementation relies on Python's standard `csv.DictReader`, which is portable but not optimal for large catalogs. For catalogs with hundreds of thousands of rows, using `pandas.read_csv()` or an indexed SQLite database would provide significantly faster random access and filtering.

# 4.20 Summary

The archive query subsystem is a lightweight yet strategically important component of the pipeline. By prioritizing a local, cached export of the NASA Exoplanet Archive, it enables rapid, reproducible, and offline retrieval of published orbital periods and planetary metadata.

Its integration with the `PeriodStage` allows literature ephemerides to guide subsequent transit searches, reducing computational cost while improving robustness. The architecture is clean and modular, but future versions would benefit from indexed storage, online synchronization, richer metadata, and support for additional exoplanet catalogs.

The next chapter follows these literature periods into the **Light Curve Download** stage, where TESS observations are retrieved from MAST and prepared for preprocessing.
